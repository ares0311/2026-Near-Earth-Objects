# Operator Objective for the NEO Harness

This file is the canonical project-level interpretation of the operator's
original harness request. Scientific processing domains are subordinate content;
they do not define the harness architecture.

## Desired product

Produce a clean Spec Prompt system that lets a Codex CLI coding agent take the
NeoHunter repository from its clean baseline to a production-quality CLI while
making the fewest possible unverified decisions and consuming minimal context.

The Spec Prompt consists of a short launch prompt backed by a compact hierarchy
of Markdown runbooks and machine-readable TOML/JSON/YAML configuration. Together
they must provide all verified evidence, mathematics, schemas, business logic,
tests, adversarial roles, data-source instructions, and implementation sequencing
before the coding agent needs them.

## Required harness layers

1. **Agent-control layer** — minimal prompts, instruction hierarchy, authority,
   context routing, token discipline, role separation, and stop conditions.
2. **Product layer** — `/NeoHunter`, command autocomplete, `/New Search`,
   `/Review Search Logs`, `/Follow-On Search`, `/Exit`, parameters, filtered-grid
   behavior, dark-terminal presentation, progress tables, and UX acceptance.
3. **Data and access layer** — exhaustive applicable astrometric source registry,
   verified URLs, product schemas, quantitative applicability, rate/storage terms,
   credential and macOS Keychain procedures, and no-guess interface contracts.
4. **Scientific-method layer** — independently sourced classical and frontier-AI
   methods appropriate to each data source, with exact mathematics, limitations,
   training/evaluation evidence, and implementation specifications.
5. **Persistence and operations layer** — search-result database, restartability,
   sharding/workers, 100 GB active-storage ceiling, telemetry, ETA reporting,
   deterministic non-LLM runtime, and failure recovery.
6. **Adversarial-validation layer** — scientific red teams for every equation,
   method, data interface, implementation, and claimed detection; a second-order
   validator for the primary adversarial process; matched legitimate controls;
   and production promotion gates.
7. **Detection disposition layer** — follow-up, rejection/reclassification,
   independent verification, evidence packaging, and operator-gated scientific
   submission/publication preparation without autonomous submission or authority
   contact.
8. **Implementation-handoff layer** — a topologically ordered Codex CLI assignment
   that supplies prerequisite evidence before use and prohibits invention.

## Relationship of the seven scientific domains

The accepted v3 source listed point-pixel detection, trail detection, catalog
association, single-night tracklets, multi-night/cross-survey linking, historical
recovery/precovery, and initial-orbit uncertainty handling. These are candidate
scientific-method domains within layers 3, 4, and 6 above.

They matter only where research establishes that a NeoHunter search or follow-up
workflow needs them. For each applicable domain, the harness must provide exact
data sources, equations, schemas, business rules, tests, and adversarial evidence.
They are not seven harness phases, do not independently authorize work, and do
not replace the product, data, operations, UX, or agent-control requirements.

## Authority and execution boundary

Harness construction may research and specify the entire path to production. It
must not implement the application, acquire scientific payloads, execute searches,
create credentials, submit findings, contact authorities, or make discovery or
impact claims. Credential creation, data acquisition, implementation, and any
submission require their later operator-gated steps specified by the harness.
